## 当前架构基线与范围边界

1. `owner_instance_id` 为唯一 owner 真源；`pack_<instance_id>` 只为 UI/protocol ID，绝不从字符串反推、补写或授权 owner。
2. `classify_container_ownership`/`find_live_container_owner` 是唯一 resolver。静态 allowlist 仅 `body_pocket`、`main_pack`、`small_pouch`、`front_satchel`；live owner 仅 worn、held、hotbar、`body_pocket`。其它 grid、任意 `pack_*` 与 owner 自身容器不可作为 live surface。
3. 每个 `InventoryLocationV1::Container` from/to 先过同一结构门；from 不做 filter，to 才做 filter；owner 进入自身 `pack_<owner_id>`（move/swap 两方向）为 typed `ContainerOwnerSelfContainment`，零副作用。
4. `resolve_item_category(item,item_registry,mineral_registry)` 是唯一 category authority：registered template 取 canonical category；未注册仅 canonical `mineral_id`、registry hit、精确 `mineral_<canonical>` template 三者齐备才 Mineral；spoof/unknown/mismatch typed invalid，绝不 fallback `Misc`。
5. `water_skin` 已移出 scope，仅保留“历史移交 satiety/hydration”的说明；不得出现于容器数量、grid/filter、`ContainerSpec`、阶段交付、测试或 PR scope。`trade_crate`/`dead_drop_box` 是 placeable 边界，`herb_crate_placed` 为独立 placed twin，P3 不实现转换。
6. nested/session 容器路线已否决，唯一玩家移动入口仍是 `InventoryMoveIntent`；forge runtime session 只投影 durable `ForgeAttemptId`。
7. P1A 固定内部 `ContainerAcceptanceLockReason::{OwnerMissing, OwnerNotFound, OwnerInvalid}`，判定口径即上第 2 条 resolver 的 owner allowlist/eligible surface 三态；P2 持久化 `integrity_lock.reason` 与 P4 `acceptance_lock.reason` 均取该类型，wire 编码见 P4。

## P1A — process-local owner/filter prepared core 🔄

### 可核验交付物

1. 在 `server/src/inventory/mod.rs` 固定 `classify_container_ownership`、`find_live_container_owner`、`resolve_container_acceptance`、`resolve_item_category`，落实上述 allowlist、eligible surface、typed corruption、目标 filter OR；`rebuild_containers_from_equipment` 复用它。
2. 版本化 owner migration 替换 load-time prefix backfill：从 `inventories.schema_version` v2 起，严格 parser 只接受 canonical `pack_<u64>`，拒 `pack_01`/空白/符号/溢出；仅唯一 eligible live owner 且有效 `ContainerSpec` 可写 `owner_instance_id`。inventory JSON SQLite commit 成功后才升版；失败保留 pending；不 bump revision、不发 snapshot。
3. `PreparedInventoryMutation<'a>` 为 private、non-Clone、`#[must_use]` 的借用 process-local **单 `PlayerInventory`** 载体：prepare→`commit_prepared_inventory_mutation(self, drops: &mut DroppedLootRegistry, outcomes: &mut EventWriter<InventoryMoveOutcome>) -> CommittedInventoryEffects` 独占 `&'a mut PlayerInventory`。prepare 只持 staged inventory、route、merge/push、`Vec<PreparedInventoryDrop>`、一次 outcome 与 debug `original_revision`；commit 的调用 handler 是唯一 effect owner，显式传入仍由其持有的 drop/outcome sinks，替换 inventory 后不可失败地安装 effects。载体不得存 resource/event、跨 handler/tick/DB 或并存，revision 恰 +1；无 CAS。
4. `PreparedInventoryMutation` **只**服务普通 process-local 单 inventory move/swap/非 durable ingress。它不是 crash atomic，也绝不神奇覆盖 multi-resource：`ExternalContainerPreparedMove`（player+`ExternalContainer`）、`PreparedPlayerTransfer`（source+target `PlayerInventory`+`DroppedLootRegistry`+`DropContext`）、`PreparedOwnerLossSpill`（owner inventory+drop registry+outcome）及 `PreparedBoneCoinTransaction`（inventory+bone-coin storage+ledger+drop+event）是各自显式命名、只在调用方同时独占全部参与资源期间构造并 commit 的 carrier。每种 carrier 列出 staged candidates、唯一 commit owner、每个 player revision +1 的规则；prepare 任何失败或 commit 前退出时所有参与资源深比较不变。P1B `PreparedInventorySettlement` 另行持久化，禁止调用上述任一 process-local commit。
5. 新增 `PreparedInventorySettlement`：owned、可序列化、无 live borrow、不得直接 commit/outcome；以同一 resolver/filter/fit/drop policy 产生 P1B WAL 所需 candidate `PlayerInventory`、candidate `SkillSet`、candidate drops/result/source/station snapshots，交给 P1B 唯一 durable commit API。不得让 borrowed mutation 跨 tick/SQLite。
6. P1A 的 `InventoryItemPrepareFn` 仅原样携带 freshness 字段；不得执行 Freeze/Normal 或任何 transition。ordinary move/swap、owner-loss spill/drop、durable settlement 同样遵守；P2 才替换/扩展 hook。
7. 普通 move/swap、四 automatic ingress 与非 durable `_or_ground` ingress 仅可使用 `PreparedInventoryMutation`。`ExternalContainer` 双资源 move 固定用 `ExternalContainerPreparedMove`；owner-loss（discard/morph/backpack break）固定用 `PreparedOwnerLossSpill` 做 detach→rebuild→spill→drop→outcome；death/TSY death、broken recovery、remains、treasure deactivate、trade、full transfer、bone-coin 按第 4 项各自的 explicit multi-resource carrier。每条路径的 prepare 失败均不得改变任一 live resource，成功 revision 按各自 carrier 的规则精确推进。
8. `transfer_all_inventory_contents` 固定用 `PreparedPlayerTransfer`，live owner 交易必 `ContainerOwnerTradeForbidden`；bone coin craft 固定用 `PreparedBoneCoinTransaction`，且其 ledger transfer 继续走 `qi_physics::ledger`。NPC/world 自产不是玩家 ingress。
9. 不新增、不迁移、不锁定、不验收 snapshot sender；不要求 EventWriter/outbox/final snapshot once；保持既有 request/resync 给 P2。

### 饱和测试

普通 `PreparedInventoryMutation` 的 new/partial/full merge、move/swap 双向 filter、self-containment、owner-loss/rebuild/spill/drop、每种非 durable ingress；`ExternalContainerPreparedMove`、`PreparedPlayerTransfer`、`PreparedOwnerLossSpill`、`PreparedBoneCoinTransaction` 分别做 compile/API pin，证明只能在持有其全部命名资源时 commit、effect sink 只能消费一次。每个 carrier 覆盖成功 revision 精确 +1 和每一 resolver/category/bounds/collision/weight/drop-context/ledger 前置失败的所有参与资源深比较不变；ordinary drop/outcome 恰一次。另 pin private non-Clone `#[must_use]`、活借用期间不能二借/改 revision/layout；freshness raw 字段完全不变；不测 transition、snapshot sender/outbox/final snapshot。

### A. Physical ordinary 与 entity-backed durable placement settlement

1. dispatcher 对 ordinary Start/Terminal 在授权前经 `DurablePositionOccupancyResolver` 捕获且验证 `BreakAttemptSnapshot.target_identity: TargetIdentity`，而非只缓存 AIR/`BlockState`：resolver 必同时读取 `(dimension,pos)` claim、placement manifest（含 placement/generation/kind）与完整 `ChunkLayer BlockState`，并且只产生**恰一个**身份。无 claim 且 canonical physical state 存在时为 `PhysicalBlock { dimension, pos, state: BlockState }`；唯一相符的 claim、placement row/hash 与 canonical entity-backed projection（AIR 或明列 marker projection）时为 `EntityBacked { placement_id: EntityBackedPlacementId, generation: u64, dimension, pos, kind: EntityBackedTargetKind }`。claim+non-AIR physical block、多个 claim、claim/placement row/generation/kind/hash 不一致、manifest 与 layer projection 不一致均为 typed `DurableBlockIntegrityFault` / `PositionOccupancyQuarantined`：禁止任意挑选 PhysicalBlock 或 EntityBacked，禁止 break/drop/contents mutation/claim release，只有既有审计的 operator repair 可以收敛。`ExternalContainer` session/`FurnitureRegistry` visual 只可绑定并复核 entity-backed identity，绝不可代替 target identity；social `SpiritNicheRegistry` 的 Start/Stop reveal 及 spiritwood 均为 physical-world consumer，不可错误改成 marker identity。`Entity::to_bits()`、`placed_at_tick`、session ID 和 transient `Entity` 均不得作跨 tick/reload identity。
2. P1B 新增 SQLite authoritative `entity_backed_placeable_placements` 和唯一权威 `active_position_claims`。claims row 以 `(dimension, x, y, z)` 作主键，并持 `placement_id`、`generation`、kind、claim schema/audit；**Active 与 WardSuppressed 都持续持有同一跨-kind claim**，`Removed` 才不持有。禁止 partial `UNIQUE WHERE lifecycle_state='Active'`、按 kind 分表 unique 或任意第二 namespace。StorageCrate、DeadDrop、Workbench 的 placement 在 `BEGIN IMMEDIATE` 内先写 placement row 与 claim；claim/CAS 失败即 typed `EntityBackedPositionOccupied`，零扣放置物、零 manifest、零 session 分配、零 marker spawn。placement row 固定含 `placement_id UUIDv7 TEXT PRIMARY KEY`、generation、dimension/x/y/z、kind、`lifecycle_state Active|WardSuppressed|Removed`、`placer_player_id CanonicalPlayerKey TEXT NOT NULL`、nullable canonical `ward_owner_player_id`、ward_active、terminal_disposition、visibility、revision、schema_version、audit timestamps；ExternalContainer 另以 versioned `external_container_contents` FK（placement_id、contents_revision、canonical ContainerState/items payload、payload SHA-256）保存真实 contents。`opened_by`、session_id、registry entity 和 timeout 仅 runtime：重启一律 closed，从 canonical contents/revision 创建新 marker 与新 session，绝不持久化或复用旧 session。

   **坐标占用唯一权威 / resolver 冻结**：`active_position_claims` 是 `(dimension,pos)` 上 StorageCrate、DeadDrop、Workbench 处于 `Active|WardSuppressed` 的唯一 durable entity-backed 占用真源；`DurablePositionOccupancyResolver` 是唯一允许把该 claim、placement manifest 与 `ChunkLayer` 的完整 `BlockState` 合并为可写/可 dig 结论的入口。它不是“三种 marker 互撞”检查：每个普通 vanilla/Bong physical `BlockPlace`、world mutation、以及任何 placeable，**在扣物、`ChunkLayer` 写入、WAL/receipt/outbox 写入或任一 live projection 前**都必须查询同一 resolver。命中 active/ward claim 必 typed `EntityBackedPositionOccupied`，并保证 inventory、layer、WAL、receipt/outbox、manifest、claim、session/marker 均零副作用。hydrate/recovery/worldgen/runtime block writer 也只能经该 resolver；没有动态查询能力的静态写入点必须由可审计 static pin 明确列出并证明不能触及 durable-claim 坐标，禁止任何绕过。

   entity-backed create 除 claim CAS 外还必须在同一 canonical transaction 以 resolver 复核 target `ChunkLayer` 的 expected `AIR`（或本契约明列、与 placement kind 一一对应的 canonical marker projection）；任何非 AIR physical state 都 typed `PhysicalBlockPositionOccupied`，零 placement/claim/contents/WAL/扣物/marker。该双门使先存在物理块与先存在 entity-backed claim 都不能被另一方覆盖；claim-vs-physical-place 以同一 transaction/linearization key 串行，绝不以“随后 reconcile”补救。
3. **仅 resolver 已产出并冻结 `PhysicalBlock` 的** terminal 构造 private、`#[must_use]`、non-Clone 的 `PreparedOrdinaryBreak`，并由 process-local 单 tick `commit_prepared_ordinary_break` 作为唯一 commit owner：commit 前再次以同一 resolver 复核 receipt、live dimension/position/full state，确认不存在 entity-backed claim 后才原子安装 AIR、ordinary return/drop、预留 allocator 结果、furniture effect 与 `OrdinaryBreakApplied`。target 消失/替换、layer/dimension/state 不符或 receipt 已存，均 typed `DuplicateOrdinaryBreak`/`StaleAuthorizedBreak`，零副作用；任何 claim/row/hash/projection 冲突保留 resolver 的 `DurableBlockIntegrityFault`/`PositionOccupancyQuarantined`，绝不得借 ordinary 路径清 AIR。`PreparedOrdinaryBreak` 不得承载 EntityBacked、placement row、contents、ward、marker、session 或任何 durable receipt；清除把 entity-backed 也称为“同 tick process-local 不可失败”的路线。

### A.1 Canonical account key、角色世代 key 与轮换原子网关（所有 placement settlement 的前置）

1. 身份分两层且不得混用。`CanonicalPlayerKey` 是**账号认证 key**：唯一外部格式仍为当前 `player::state::canonical_player_id(username)` 产生的严格 `offline:<username>`，只用于 login/owner/online `Username` binding 与安全派生 bare username。`PlayerCharacterKey { canonical_player_key: CanonicalPlayerKey, current_char_id: Uuidv7 }`（或等价受控 DB character generation ID）是**完整角色世代 key**：只允许从已认证账号 key 加同一 SQLite transaction 中 `player_core.current_char_id` 构造；用于 `canonical_player_combat_state`、所有 combat reservation、`PlayerCombatMutationGateway`、ward roster/authorization、`DurableWardEffectApplication`、`WardEffectId`、recipient progress、combat recovery/outbox 与 projection receipt。`player_character_id(username,current_char_id)` 只可作既有角色展示/历史 ID；其带 suffix 的内部形状绝不回传到外部 parser，也不得替代 typed `PlayerCharacterKey`。
2. `parse_offline_canonical_player_id` 只解析**外部认证 account ID**：仅接受精确单一 `offline:` 前缀及一个非空 username，复用 join/login 的生产 `Username` 验证，拒绝空值、重复/嵌套 prefix、冒号 suffix、空白和 mismatch，且不 trim/lowercase/Unicode normalize。该“拒绝 character suffix”规则只约束客户端/外部 canonical string；不得误拒经 `player_core.current_char_id` 已验证的内部 character generation。`player_username_from_character_id` 的 legacy suffix 语义不得被当作 parser、owner 授权或 combat key 构造器。
3. `inventories.username`、`player_skills.username` 与现有 account-slice `player_cultivation`/`player_slow` 等表继续使用 bare username，禁止把完整角色 ID 或 `offline:<username>` 写作这些主键，也禁止创建 shadow inventory/skill row。唯一 transaction-local account binding helper 必须先认证/parse `CanonicalPlayerKey`，派生 bare username，再在同一 `BEGIN IMMEDIATE` 对拍 `player_core.current_char_id`、inventory/skill before revision/hash 与 candidate；combat 表则以 `(canonical_player_key,current_char_id)` 复合唯一键及 generation/hash 对拍。账号行可按既有新生规则重置，但旧角色 combat row 绝不覆盖、合并或 hydrate 到新 generation。
4. 新增唯一 durable settlement-first `rotate_player_character_generation`/`PlayerCharacterRotationGateway`。`RevivalActionKind::CreateNewCharacter → combat::lifecycle::reset_for_new_character`、join attach 发现 terminated life 的自动转世，以及任何未来 `player_core.current_char_id` writer（含 import/repair）都只能先 insert-or-verify durable `PlayerCharacterRotationRequest`/`Pending` receipt：稳定 request ID、`CanonicalPlayerKey` account key、expected old char ID、payload SHA-256 与请求版本；同 request/同 payload restart/retry 只返回同一 pending/final outcome，payload 或 expected generation 不同 fail-closed/quarantine。**唯一协议是 settlement-first**：request 已落 Pending 后，只要该账号 inventory/skill、old `PlayerCharacterKey` combat，或 old generation 关联 mineral/forge source、station、entity placement contents 的任一 `Prepared|CommittedPendingInstall` settlement reservation 尚在，绝不改 `current_char_id`、account slices、old/new combat 或 ECS；`RotationBarrier`/`InventorySettlementRecovery` 必枚举全量 reservation 及其 owner settlement IDs，并先按各 settlement immutable candidates 完成既有 terminal，或按已冻结的合法 compensation/repair 达到唯一终态、exactly-once 释放全部关联资源。rotation 不得抢占、猜修或自行释放 reservation；`QuarantinedCorrupt` 必由 operator repair/compensate 收敛后才可继续。pending 期间新 old-generation combat/inventory/skill mutation 与新 old-generation settlement 一律 typed `CharacterRotationPending`，已有 settlement 只能由 recovery 收敛。

   仅当 barrier 在同一 transaction 证明该集合为空，gateway 才在**一个 `BEGIN IMMEDIATE`**中获取 account inventory/skill、old+new combat 与 character-rotation reservations，写 immutable old-generation fence，禁止其后任何新 settlement 绑定 old generation；以 expected old generation CAS `player_core.current_char_id` 到新 UUIDv7；terminal/tombstone old generation 的 `canonical_player_combat_state`；创建带 default `CanonicalPlayerCombatSnapshotV1 { Wounds, StatusEffects, Contamination, lifecycle }` 的新 generation；并写新生 account-slice candidates、final rotation receipt 与 receipt-gated outbox。commit 后新请求只能绑定 new generation；旧 settlement/replay 按已冻结 terminal outcome 读取，绝不得安装或回灌到 new generation。所有 row 以 rotation request ID + account + expected old generation insert-or-verify；commit 前 ECS、`player_core`、combat row、reservation、receipt/outbox 对外均零可见；SQL/CAS/serialization 任一失败全部回滚，禁止先换 `current_char_id` 后 reset/save。
5. 对旧 generation 的**普通 combat writer、pending ward recovery、delayed combat/outbox projection、reconnect hydrate**统一以 `PlayerCharacterKey` expected generation 检查。旧 key 不等当前 `player_core.current_char_id` 或 old row 已 terminal/tombstone 时，绝不写新 row：普通 writer typed `StalePlayerCharacterGeneration`/terminal cancel；ward/recovery 按 immutable authorization 写明确 `CancelledByCharacterRotation` terminal/compensation（先验证/写应有 before disposition，再释放对应旧 reservation）；同一 `WardEffectId`/receipt 绝不能仅以 account key 去重或改投新角色。若 rotation 已 final，旧 `Prepared` settlement/recovery 仅完成它已绑定旧 generation 的 terminal cancellation/compensation，不得恢复为新 generation 可写。
6. hydrate 只从 `player_core` 当前 `current_char_id` 指向的同 `(CanonicalPlayerKey,current_char_id)` combat row读取，并核验 row lifecycle、revision、payload hash、character generation、rotation receipt 与 reservation 状态；缺 row 只可经 rotation/new-account transaction 的 default snapshot 创建，错误/旧/双 current row quarantine、拒绝 attach，绝不 fallback 到账号级 `offline:<username>` row、legacy character string 或 live ECS。response loss、crash/restart/reconnect 与 duplicate CreateNewCharacter/auto-rotation request 均以 rotation receipt 返回/重放同一个 `PlayerCharacterKey`、同一 default snapshot/outbox，绝不二次轮换、重置、释放 reservation 或投影。

### A.2 Canonical player account key binding（placement owner/inventory/skill 前置）

1. 新增 exact `CanonicalPlayerKey` 与 `parse_offline_canonical_player_id`；唯一 canonical 格式是现有 `player::state::canonical_player_id(username)` 产出的 `offline:<username>`。WAL、reservation、placement `placer_player_id`/`ward_owner_player_id`、receipt、online entity identity mapping 一律存/比 `CanonicalPlayerKey`，禁止 Entity、character suffix 或裸 username 充当 durable owner identity。
2. parser fail-closed：只接受精确单一 `offline:` 前缀及一个非空 username；拒绝空值、空 username、第二个/嵌套 prefix、任意 `:` character suffix、前后或中间额外字符与不符合生产 `Username` 约束的值。它必须复用/抽取当前 join/login 所采用的生产 username 验证规则，不得自行 lower-case、trim、Unicode normalize 或发明额外 normalization；大小写和可变语义完全忠实生产输入。`player_username_from_character_id` 的“允许 suffix”语义不得被误用为本 parser。
3. `inventories.username` 与 `player_skills.username` 的 SQLite 主键保持裸 username，绝不得直接把 `offline:<username>` 作为主键。唯一 transaction-local binding helper 先 `parse_offline_canonical_player_id`，再用已验证的裸 username 调 `load_player_inventory_from_sqlite`/`persist_player_inventory_json_in_transaction` 与 skill helper；它在同一个 `BEGIN IMMEDIATE` 内对拍 canonical key→username、inventory/skill row、before revision/hash，之后才能安装 candidate。canonical key、row username、online `Username`→canonical key 任何不一致均 typed fail-closed、零副作用。
4. online、offline、crash/restart 都只读写同一份 hydration-visible `inventories`/`player_skills` row：online live install 先以 entity `Username` 映射同一 `CanonicalPlayerKey`，canonical install 仍落同一裸 username row；offline/recovery 以 parser binding 直接落该 row；不得造 canonical-key shadow row、复制 row 或在 reconnect 时合并。测试锁 online/offline/restart 同一 row、malformed/suffix/重复 prefix/username mismatch 全拒绝且 placement/claim/inventory/skill/outbox 零变化。

### B. Durable finality 与延迟 projection 分离

1. terminal worker 只校验 immutable Prepared WAL 后 CAS `Prepared→CommittedPendingInstall`，不重算经济、不读 live source/session、不删 reservation。durable finality 不等待 chunk/ECS/ground entity/玩家未来重连。
2. `DurableInstallReceipt` 只覆盖一个 SQLite `BEGIN IMMEDIATE` 能原子安装的 canonical state：`inventories`/`player_skills` terminal snapshot、mineral source 或 forge attempt/station、`durable_block_ownership` manifest、WAL terminal data 与 stable `ground_drop_outbox` rows。`ProjectionOutbox`/`ProjectionReceipt` 是单独层，只含 chunk block、ECS/index、ground-drop entity、未来 hydration 的 projection id/hash；不得作为 economic acknowledgement 前置。
3. **在线 player 唯一顺序**：reservation 后，唯一 exclusive install worker 经 `SkillMutationGateway` 持有 live `PlayerInventory`/`SkillSet`；仅 before revision/hash 对拍才安装 WAL after candidate，并以 settlement ID + target revision/hash 写 process `LiveInstallReceipt`。Prepared、terminal→live install、live install→canonical install、canonical install→ack 的每个窗口，所有普通 writer 先过 gate 并 typed `SettlementReserved`。接着同 worker 在 `BEGIN IMMEDIATE` 对拍 WAL/LiveInstallReceipt/canonical before 后安装 canonical targets + DurableInstallReceipt/outbox，随后同 transaction ack 并 delete reservations exactly once。live 已装而 canonical 未装时 crash，recovery 仅按 hash/receipt 重放，不许 autosave 或其它 writer 抢跑。
4. **离线 player 唯一顺序**：无 live target，terminal/recovery 直接在同一 SQLite transaction 安装 canonical after snapshot、DurableInstallReceipt/outbox，ack 后释放 reservation；未来 hydration 只读 DB terminal snapshot，绝不因离线等待 reservation。
5. ack 后立即释放经济 reservation：chunk 永不加载、player 永不重连、ground entity 未 spawn 均不能滞留。`ProjectionOutboxKey` 是唯一 canonical identity，精确定义为 `(settlement_id TEXT UUIDv7, payload_ordinal INTEGER)`：`InventorySettlementId` 沿用生产 durable UUIDv7 字符串表示（`Uuid::now_v7().to_string()`），`payload_ordinal` 为该 immutable settlement payload 内从 0 起的非负序号；SQLite `ground_drop_outbox` 必须 `UNIQUE(settlement_id, payload_ordinal)`。projection/replay 首先按此复合键读 row：同 key 且 payload SHA-256 相同才 idempotent，same key/hash 不同一律 `ProjectionQuarantine`；禁止用 `hash(settlement_id,payload_ordinal)` 当 entity、instance 或幂等 identity。
6. `InventoryInstanceIdAllocator` 的 durable version 是**全部** `ItemInstance`、`DroppedLootEntry` 与 `GroundProjectionSurrogateId` producer 的唯一全局线性化 authority；不得为 settlement/outbox surrogate 建第二 allocator、第二 high-water 表或直接自增。现有 `inventory/mod.rs:598-638` 内存 `next` 与 `player/state.rs:3813`/`persistence/mod.rs:5682-` 的 JSON scan high-water 只为迁移基线，P1B 后不得作为 allocation authority。SQLite 建唯一 global sequence row（JS-safe `next_id`）及 `inventory_instance_id_leases(lease_id, owner, process_epoch, start_id, end_id, next_id, consumed_at/created_at)`：每次 runtime allocator 取 lease 在 `BEGIN IMMEDIATE` 内 CAS 推进该唯一 sequence 并持久记录不重叠闭区间 `[start_id,end_id]`；内存 `next_id` 只能消费自己 durable lease。崩溃后的未消费 ID 可永久跳过、绝不回收/转配给不同 identity；达到 `JS_SAFE_INTEGER_MAX` 前后均 fail-closed exhausted，禁止溢出或概率重试。
7. settlement canonical transaction 若需 outbox row，必须在**同一 `BEGIN IMMEDIATE`**先以该 global sequence 为 `(settlement_id,payload_ordinal)` reserve/consume 一个 surrogate，再写 composite-key→surrogate mapping、outbox/WAL/receipt；live allocator lease 也只从同一 sequence 预留。启动/restart 不得从 inventories/dropped JSON 推导或回拨 sequence。因而 settlement→ordinary、ordinary→settlement、并发 lease、crash/restart 均不可重号；同一 composite key 仅在完整 persisted identity + payload SHA-256 相同下幂等返回既有 surrogate，否则 typed quarantine/fail-closed，绝不以 hash 充当 ID。
8. `DroppedLootRegistry` 必须封装 collision-checking `insert_checked`：ID 缺失才插入；同 ID 且完整 `DroppedLootEntry` identity/payload hash 一致才 idempotent；同 ID 异主、异 composite key 或异 payload hash 返回 typed collision 并零覆盖。SQLite `dropped_loot`、outbox surrogate mapping 与 hydration 同样采用 insert-or-verify（禁止现有 `persistence/mod.rs:5594-5631` 的 `ON CONFLICT(instance_id) DO UPDATE` 覆盖）；load 的 `HashMap::insert` 先做同一 identity/hash 校验。P1B 静态 gate 禁止生产 `DroppedLootRegistry.entries.insert`、`HashMap::insert` 对 durable loot、`INSERT OR REPLACE` 与该 UPSERT 形态；仅 registry checked API、受控 test fixture 和 migration adapter 可出现。
9. **生产迁移清单（不可省略）**：把 `inventory/mod.rs::{spawn_template_dropped_loot,inventory discard/owner-loss/external-container}`、`mineral/inventory_grant.rs`、`forge/inventory_bridge.rs`、`alchemy/danxin.rs`、`botany/{mod,harvest}.rs`、`fauna/{drop,daozhan,dying_elder,bone_coin}.rs`、`npc/{loot,tsy_hostile,dormant/relic_hydrate}.rs`、`world/{block_drop,container_block,loot_pool,tsy_container_search,spawn_tutorial}.rs`、`craft/workbench.rs`、`coffin/mod.rs`、`lingtian/systems.rs`、`spiritwood/mod.rs`、`supply_coffin/interact.rs`、`zhenfa/mod.rs`、`combat/{lifecycle,tuike}.rs`、`network/{client_request_handler,craft_emit,tuike_ash_emit}.rs`、`cmd/dev/{give,block_picker}.rs` 的所有 runtime `next_id`/ItemInstance producer 改走同一 lease API；把 `inventory/mod.rs`、`inventory/tsy_loot_spawn.rs`、`fauna/{drop,daozhan,dying_elder}.rs`、`npc/{tsy_hostile,dormant/relic_hydrate}.rs`、`world/container_block.rs` 和 durable hydration 的所有 `DroppedLootRegistry.entries.insert` 改为 `insert_checked`。`inventory/mod.rs:867` 的 resource 初始化改为 durable lease bootstrap，`persistence/mod.rs` migration/transaction helper 成为唯一 sequence/lease/mapping writer；用 static pin 覆盖上述路径和全 `server/src`，不允许漏网 direct producer/insert。
10. startup/recovery 固定 settlement-first 顺序：先 hydrate `DurableBlockOwnershipIndex`、canonical receipt/outbox，再由 `InventorySettlementRecovery` 枚举并完成 `Prepared|CommittedPendingInstall` 的 immutable terminal/recovery；若同账号/旧角色已有 `PlayerCharacterRotationRequest::Pending`，`RotationBarrier` 必收集 inventory/skill、old combat、source/station、placement contents 的全量 reservation 与 owner settlement IDs，并等待每个 settlement 按既有 terminal 或已冻结 compensation/repair 收敛唯一终态。`QuarantinedCorrupt` 只能由 operator repair/compensate，rotation 不得绕过。集合为空且防 TOCTOU 后才在同一 `BEGIN IMMEDIATE` 写 old-generation fence、取得 rotation reservations 并 CAS `current_char_id`；此后新 settlement 只能绑定 new generation，旧 replay 只能读取其 terminal outcome、绝不安装到新 generation。最后 player attach/hydrate/block writers 才启动；ProjectionOutbox 可以无限期等待 chunk/player 可用而不阻塞 settlement finality。

### C. `QuarantinedCorrupt` 审计终结路径

1. WAL/receipt 持 before、after、所有 target schema/hash/revision、install marker 与 evidence hash；不一致进入 `QuarantinedCorrupt` 并保 reservation，禁止 after-only 和模糊幂等覆盖。
2. 唯一入口是 operator-only server-side `SettlementRepairAuthority`，不暴露普通 C2S。durable `SettlementRepairRecord` 记录 actor/reason/time、expected quarantine revision CAS、evidence hash、schema migrator version、完整 target hashes 与 action；状态唯一为 `QuarantinedCorrupt→RepairPrepared→CommittedPendingInstall|CompensatedTerminal`。
3. 自动规则固定：canonical targets 全等 after 且 install marker 存在，rebuild receipt 后继续 commit；全等 before 且无 marker，仅经已验证 schema migrator retry immutable candidate；mixed/unknown 必须由 operator 从备份提交一套完整 coherent snapshot，验证全部 target hashes 后选择 `CommitAfter` 或 `CompensateBefore`，禁止局部拍脑袋修。
4. `RepairPrepared` 仍持 reservation，repair/restart 以 repair record + expected revision CAS 幂等；只有最终 ack 或 `CompensatedTerminal` transaction 可 exactly-once 释放。compensation 先写完整 before canonical snapshot/outbox disposition；恢复后资源重新经 gate 可写。
