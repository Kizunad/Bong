### P1B-A.4 Canonical account key、角色世代 key 与轮换原子网关（所有 placement settlement 的前置）

1. 身份分两层且不得混用。`CanonicalPlayerKey` 是**账号认证 key**：唯一外部格式仍为当前 `player::state::canonical_player_id(username)` 产生的严格 `offline:<username>`，只用于 login/owner/online `Username` binding 与安全派生 bare username。`PlayerCharacterKey { canonical_player_key: CanonicalPlayerKey, current_char_id: Uuidv7 }`（或等价受控 DB character generation ID）是**完整角色世代 key**：只允许从已认证账号 key 加同一 SQLite transaction 中 `player_core.current_char_id` 构造；用于 `canonical_player_combat_state`、所有 combat reservation、`PlayerCombatMutationGateway`、ward roster/authorization、`DurableWardEffectApplication`、`WardEffectId`、recipient progress、combat recovery/outbox 与 projection receipt。`player_character_id(username,current_char_id)` 只可作既有角色展示/历史 ID；其带 suffix 的内部形状绝不回传到外部 parser，也不得替代 typed `PlayerCharacterKey`。
2. `parse_offline_canonical_player_id` 只解析**外部认证 account ID**：仅接受精确单一 `offline:` 前缀及一个非空 username，复用 join/login 的生产 `Username` 验证，拒绝空值、重复/嵌套 prefix、冒号 suffix、空白和 mismatch，且不 trim/lowercase/Unicode normalize。该“拒绝 character suffix”规则只约束客户端/外部 canonical string；不得误拒经 `player_core.current_char_id` 已验证的内部 character generation。`player_username_from_character_id` 的 legacy suffix 语义不得被当作 parser、owner 授权或 combat key 构造器。
3. `inventories.username`、`player_skills.username` 与现有 account-slice `player_cultivation`/`player_slow` 等表继续使用 bare username，禁止把完整角色 ID 或 `offline:<username>` 写作这些主键，也禁止创建 shadow inventory/skill row。唯一 transaction-local account binding helper 必须先认证/parse `CanonicalPlayerKey`，派生 bare username，再在同一 `BEGIN IMMEDIATE` 对拍 `player_core.current_char_id`、inventory/skill before revision/hash 与 candidate；combat 表则以 `(canonical_player_key,current_char_id)` 复合唯一键及 generation/hash 对拍。账号行可按既有新生规则重置，但旧角色 combat row 绝不覆盖、合并或 hydrate 到新 generation。
